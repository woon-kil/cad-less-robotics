# 바이트 순서 — 쓰기 경로의 주석 처리된 스왑 (D1 후보 검사)

`Arm_serial_servo_write` 세 분기 모두에 **주석 처리된 바이트 스왑**이 있다.

```python
pos = int((3100 - 900) * (angle - 0) / (180 - 0) + 900)
# pos = ((pos << 8) & 0xff00) | ((pos >> 8) & 0xff)      ← 비활성
value_H = (pos >> 8) & 0xFF
value_L = pos & 0xFF
```

`write6`·`write_any`·`bus_servo_control` 에도 같은 주석이 반복된다. **활성화된 곳은 한 군데도 없다.**

읽기 경로에는 **활성화된 스왑**이 있다.

```python
pos = self.bus.read_word_data(self.addr, id + 0x30)
...
pos = (pos >> 8 & 0xff) | (pos << 8 & 0xff00)            ← 활성
```

이 비대칭이 D1(wrong byte order) 후보인지 검사했다.

## 분석

Linux SMBus `read_word_data` 는 2바이트를 읽어 **먼저 수신한 바이트를 반환 워드의 하위에** 놓는다. 따라서 라이브러리가 읽기에서 스왑한다는 것은, **장치가 상위 바이트를 먼저 보낸다**(big-endian)고 해석한다는 뜻이다.

쓰기는 `[value_H, value_L, …]` 순서로 보낸다. 블록 데이터는 리스트 순서대로 나가므로 **상위 바이트가 먼저** 나간다 — big-endian.

| 방향 | 와이어상 첫 바이트 | 해석 |
| --- | --- | --- |
| 읽기 (스왑 **활성**) | 상위 | big-endian |
| 쓰기 (스왑 **비활성**) | 상위 | big-endian |

→ **두 방향이 일치한다.**

주석 처리된 스왑을 **활성화하면** 쓰기가 little-endian이 되어 읽기 해석과 **어긋난다.** 즉 비활성 상태가 올바른 쪽이다. 주석은 개발 흔적이고 결함이 아니다.

## 판정

**D1 아님.** 바이트 순서 결함 근거를 찾지 못했다.

보강: 같은 big-endian 쓰기 인코딩이 벤더가 배포하는 그대로이고, 공식 코스가 이 API 를 정상 경로로 제시한다. 벤더 예제가 동작한다면 이 인코딩이 맞다는 뜻이다.

## 🔴 이 분석이 의존하는 전제

`read_word_data` 의 바이트 순서(먼저 수신 = 하위)는 **Linux SMBus 규약**에 근거한 것이고, 이 세션에서 실측으로 확인하지 않았다. 다만 전제가 반대라 하더라도 **두 방향이 함께 뒤집히므로 일치 결론은 변하지 않는다** — 읽기 스왑과 쓰기 비스왑이 같은 방향을 가리킨다는 구조는 유지된다.

읽기 경로는 이 장비에서 **1,290회 이상 성공**했고 반환 각도가 URDF 범위와 물리 자세에 모순되지 않았다. 읽기 해석이 맞다는 실측 근거이고, 쓰기가 같은 endianness 를 쓴다는 것이 이 분석의 핵심이다.
